1. Vue d'Ensemble de l'Architecture

L'application "PackingList Pro" est une application web PHP développée sans framework majeur ("PHP Vanilla"). Elle adopte une structure inspirée du modèle MVC (Modèle-Vue-Contrôleur) pour organiser le code et séparer les préoccupations.

  • Modèle (Model) : Gère les données et la logique métier. Interagit avec la base de données MySQL. Les modèles se trouvent dans src/Models/.
  • Vue (View) : Responsable de la présentation des données à l'utilisateur. Ce sont des fichiers PHP/HTML situés dans src/Views/.
  • Contrôleur (Controller) : Reçoit les requêtes HTTP, interagit avec les modèles pour récupérer ou modifier les données, et sélectionne la vue appropriée pour afficher la réponse. Les contrôleurs sont dans src/Controllers/.

Un point d'entrée unique (public/index.php) gère toutes les requêtes, qui sont ensuite dirigées par un routeur simple vers le contrôleur et l'action appropriés.

L'application utilise Composer pour la gestion des dépendances (comme les librairies pour QR code, Excel, PDF) et pour l'autoloading PSR-4.

3. Base de Données

3.1 Schéma de la Base de Données (Conceptuel)

La base de données est MySQL. Le schéma principal s'articule autour des utilisateurs, de leurs rôles et permissions, des sites, des packing lists, des palettes et des colis. Les exports théoriques sont stockés pour comparaison.

(Idéalement, insérer ici un diagramme Entité-Association simplifié si possible, ou un lien vers celui-ci)

Les relations clés incluent :

  • Utilisateurs <-> Rôles (plusieurs-à-plusieurs via `user_roles`)
  • Rôles <-> Permissions (plusieurs-à-plusieurs via `role_permissions`)
  • Utilisateurs -> Sites (un utilisateur peut être rattaché à un site)
  • Packing Lists -> Sites (une PL appartient à un site)
  • Palettes -> Packing Lists (une palette appartient à une PL)
  • Colis -> Palettes (un colis appartient à une palette)
  • Theoretical Exports -> Sites (un export théorique est pour un site)

3.2 Description des Tables Principales

Voici une description des tables les plus importantes. Pour les détails complets des colonnes, types et contraintes, se référer au script SQL de création de la base de données (database/packing_list_db.sql).

Table `users`

Stocke les informations des utilisateurs de l'application.

  • `id` : PK, auto-incrémenté
  • `username` : Nom d'utilisateur unique pour la connexion
  • `password_hash` : Mot de passe hashé
  • `email` : Email unique de l'utilisateur
  • `first_name`, `last_name` : Prénom et nom
  • `is_active` : Booléen (compte actif ou inactif)
  • `site_id` : FK (optionnelle) vers `sites.id`, site de rattachement principal de l'utilisateur
  • `created_at`, `updated_at` : Timestamps

Table `sites`

Définit les différents sites opérationnels.

  • `id` : PK, auto-incrémenté
  • `code` : Code court unique pour le site (ex: "PANTIN", "LYON01")
  • `name` : Nom complet du site
  • `address` : Adresse du site (optionnel)
  • `is_active` : Booléen
  • `created_at`, `updated_at` : Timestamps

Table `roles`

Définit les rôles utilisateurs (ex: Administrateur, Superviseur).

  • `id`, `name`, `description`, `created_at`, `updated_at`

Table `permissions`

Définit les permissions granulaires de l'application (ex: `packinglist_create`).

  • `id`, `name` (code unique de la permission), `description`, `created_at`, `updated_at`

Table `user_roles`

Table de liaison pour la relation plusieurs-à-plusieurs entre `users` et `roles`.

  • `user_id` (FK), `role_id` (FK)

Table `role_permissions`

Table de liaison pour la relation plusieurs-à-plusieurs entre `roles` et `permissions`.

  • `role_id` (FK), `permission_id` (FK)

Table `settings`

Stocke les paramètres globaux de l'application (ex: patrons de codification).

  • `id`, `setting_key` (unique), `setting_value`, `description`, `updated_at`

Table `dynamic_counters`

Gère les compteurs dynamiques pour les patrons de codification (par site, année, mois).

  • `id`, `counter_key` (unique, ex: `pl_site1_yearly_2025`), `current_value`, `updated_at`

Table `packing_lists`

Informations des listes de colisage.

  • `id` : PK
  • `site_id` : FK vers `sites.id`, site de la PL (NOT NULL après les dernières modifications)
  • `reference` : Référence unique générée (ex: PL-SITE-202505-001)
  • `ship_date` : Date d'expédition prévue
  • `status` : ENUM('open', 'closed')
  • `created_by_user_id`, `closed_by_user_id` : FK (nullables) vers `users.id`
  • `theoretical_batch_id` : (Supprimé, la liaison se fait par site/semaine de `ship_date`)
  • `created_at`, `updated_at`

Table `palettes`

Informations des palettes associées aux packing lists.

  • `id` : PK
  • `packing_list_id` : FK vers `packing_lists.id` (NOT NULL)
  • `code` : Code unique généré pour la palette
  • `qr_code_path` : Chemin relatif vers l'image QR code de la palette
  • `status` : ENUM('generated', 'open', 'closed')
  • `max_colis` : Nombre maximal de colis pour cette palette
  • `open_date_time`, `close_date_time` : Timestamps d'ouverture/fermeture
  • `created_by_user_id`, `opened_by_user_id`, `closed_by_user_id` : FK (nullables) vers `users.id`
  • `created_at`, `updated_at`

Table `colis`

Informations de chaque colis scanné.

  • `id` : PK
  • `palette_id` : FK vers `palettes.id` (NULL pour un colis enfant)
  • `package_number` : Numéro de colis unique (issu du QR code colis, contrainte UNIQUE globale)
  • `payload_json` : Contenu JSON valide (reconstruit à partir du payload brut du QR code)
  • `scan_date_time` : Timestamp du scan
  • `scanned_by_user_id` : FK (nullable) vers `users.id`
  • `type` : ENUM('parent','product') pour distinguer un colis parent d'un colis classique
  • `parent_colis_id` : FK vers `colis.id` si ce colis est un enfant
  • `client_name`, `of_number`, `order_number`, `sku`, `label`, `quantity` : Champs parsés du payload
  • `internal_reference`, `article_reference`, `unit`, `postal_code`, `line_number` : Nouveaux champs parsés du payload
  • `comment` : Champ texte optionnel
  • `created_at`, `updated_at`

Table `theoretical_exports`

Stocke les quantités théoriques attendues (importées via CSV).

  • `id` : PK
  • `site_id` : FK vers `sites.id` (NOT NULL)
  • `import_year` : Année de l'import/validité du théorique (NOT NULL)
  • `import_week` : Semaine ISO de l'import/validité (NOT NULL)
  • `of_number`, `order_number`, `sku` : Clés pour la comparaison
  • `expected_quantity` : Quantité attendue
  • `imported_at` : Timestamp de l'import effectif du fichier
  • `imported_by_user_id` : FK (nullable) vers `users.id`
  • `created_at`, `updated_at`

4. Librairies et Dépendances Externes

L'application utilise Composer pour gérer ses dépendances PHP. Les principales librairies externes sont :

  • `endroid/qr-code` : Pour la génération des images QR code pour les palettes. Version 6.0.8 utilisée.
  • `phpoffice/phpspreadsheet` : Pour la génération des fichiers Excel (.xlsx) pour l'export de la liste des colis.
  • `dompdf/dompdf` : Pour la génération des fichiers PDF à partir de HTML, utilisé pour l'export de la liste des colis.

Les dépendances frontend (JavaScript) incluent :

  • jQuery : Utilisé principalement par DataTables et pour des manipulations DOM simplifiées dans app.js.
  • DataTables : Pour améliorer l'affichage des tableaux (tri, recherche, pagination, exports). Inclut les extensions Buttons et Responsive.
  • Bootstrap 5 : Pour la structure et le style de l'interface utilisateur. Ses composants JS (comme les Modales, Dropdowns) sont aussi utilisés.
  • Font Awesome : Pour les icônes.

Ces librairies sont chargées via des CDN dans le layout principal pour le frontend.

5. Composants Clés du Backend (PHP)

Le code backend est structuré en suivant une approche inspirée de MVC, avec des modèles, des vues (gérées par les contrôleurs), des contrôleurs, des librairies de base, et des services.

5.1 Configuration (config/config.php et config/database.php)

config/config.php est le fichier central pour les paramètres globaux de l'application :

  • Configuration de l'affichage des erreurs et du fuseau horaire.
  • Définition dynamique de `APP_URL` et `BASE_URL` pour la portabilité entre environnements (local, production).
  • Définition des chemins système constants (`ROOT_PATH`, `PUBLIC_PATH`, `SRC_PATH`, `VIEWS_PATH`).
  • Paramètres de session (`SESSION_NAME`, `SESSION_LIFETIME`, etc.).
  • Constantes applicatives (`APP_NAME`, `APP_VERSION`).
  • Clés pour les messages Flash en session.

config/database.php gère la configuration de la connexion à la base de données MySQL :

  • Constantes `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_CHARSET`.
  • Construction du DSN (`DB_DSN`) pour PDO.
  • Options PDO par défaut (`PDO_OPTIONS`).
  • Fonction `getPDO()` : Fournit une instance unique (Singleton basique) de la connexion PDO.

5.2 Point d'Entrée et Routage

Point d'Entrée (public/index.php)

Toutes les requêtes HTTP vers l'application sont dirigées vers public/index.php grâce aux règles de réécriture dans public/.htaccess (Front Controller Pattern).

Ce script est responsable de :

  1. Initialiser la session.
  2. Charger l'autoloader de Composer (vendor/autoload.php).
  3. Charger les fichiers de configuration (config/config.php et config/database.php).
  4. Instancier un objet `App\Lib\Request` pour encapsuler les données de la requête.
  5. Instancier le routeur `App\Lib\Router`.
  6. Définir toutes les routes de l'application en associant des URI et des méthodes HTTP à des actions de contrôleurs.
  7. Appeler la méthode `dispatch()` du routeur pour traiter la requête actuelle.
  8. Récupérer l'objet `App\Lib\Response` retourné par l'action du contrôleur et appeler sa méthode `send()` pour envoyer la réponse au client.
  9. Gérer les exceptions globales (ex: page 404 si route non trouvée, page 500 pour erreurs serveur).

Routeur (src/Lib/Router.php)

La classe `App\Lib\Router` gère la définition et la résolution des routes.

  • Définition des routes : Méthodes `get()`, `post()` (et potentiellement `put()`, `delete()`) pour enregistrer des routes. Une route est définie par une méthode HTTP, un chemin (qui peut contenir des paramètres comme `/users/edit/{id}`), et un "handler".
  • Handlers : Le handler peut être :
    • Une chaîne au format `'NomController@nomMethode'`.
    • Un tableau `[NomCompletClasseController::class, 'nomMethode']`.
    • Une Closure (fonction anonyme).
  • `dispatch(Request $request)` :
    • Analyse l'URI et la méthode HTTP de l'objet `$request`.
    • Normalise le chemin de la requête en tenant compte du `basePath` de l'application (si elle est dans un sous-dossier).
    • Compare le chemin et la méthode avec les routes enregistrées.
    • Supporte les paramètres de route (ex: `{id}`) en les convertissant en expressions régulières pour le matching. Les paramètres capturés sont passés à la méthode du contrôleur.
    • Appelle le handler approprié via `callHandler()`.
    • Lève une exception si aucune route ne correspond (menant à une 404).
  • `callHandler(...)` :
    • Instancie le contrôleur spécifié (en ajoutant le namespace `App\Controllers\` si un nom simple est fourni).
    • Vérifie l'existence de la classe contrôleur et de la méthode.
    • Appelle la méthode du contrôleur en lui passant l'objet `Request` et les paramètres de route extraits de l'URI.
    • Retourne la `Response` générée par le contrôleur.

5.3 Requêtes et Réponses

Classe `Request` (src/Lib/Request.php)

Encapsule les données de la requête HTTP entrante.

  • Récupère les données des superglobales `$_GET`, `$_POST`, `$_SERVER`.
  • Détermine la méthode HTTP (`getMethod()`).
  • Fournit l'URI complète (`getUri()`) et le chemin normalisé sans paramètres GET (`getPath()`).
  • Méthodes pour accéder aux paramètres GET et POST (`get()`, `post()`, `allGet()`, `allPost()`, `hasGet()`, `hasPost()`).
  • Gère le décodage des payloads JSON pour les requêtes `application/json` (`json()`, `allJson()`).

Classe `Response` (src/Lib/Response.php)

Encapsule la réponse HTTP à envoyer au client.

  • Gère le contenu (`setContent()`, `getContent()`), le code de statut HTTP (`setStatusCode()`, `getStatusCode()`), et les en-têtes (`setHeader()`, `getHeader()`).
  • Méthode `send()` : Envoie le code de statut, les en-têtes, et le contenu au client.
  • Méthodes statiques factory pour créer des types de réponses courants :
    • `Response::json(...)` : Pour les réponses JSON.
    • `Response::redirect(...)` : Pour les redirections HTTP.
    • `Response::html(...)` : Pour rendre un fichier de vue simple (utilisé par `BaseController::renderPartial`).

5.4 Contrôleur de Base (src/Controllers/BaseController.php)

Classe abstraite dont tous les autres contrôleurs de l'application héritent. Elle fournit des fonctionnalités communes.

  • Propriété `$layout` : Spécifie le fichier de layout principal à utiliser (par défaut layouts/admin_app.php). Peut être surchargé par les contrôleurs enfants.
  • Méthode `authorize(string $permissionName, ...)` :
    • Vérifie si l'utilisateur connecté (via `Auth::can()`) a la permission spécifiée.
    • Si non autorisé, définit un message flash d'erreur et effectue une redirection (terminant le script).
  • Méthode `view(string $viewPath, array $data, ...)` :
    • Méthode principale pour rendre une vue de contenu à l'intérieur du layout.
    • Injecte des données par défaut (`appName`, `baseUrl`, `pageTitle`) à la vue et au layout.
    • Appelle `renderPartial()` pour obtenir le HTML de la vue de contenu.
    • Appelle `renderPartial()` à nouveau pour le layout, en lui passant les données et le contenu de la vue.
    • Retourne un objet `Response` avec le HTML complet.
  • Méthode `renderPartial(string $filePath, array $data)` :
    • Inclut un fichier de vue PHP et capture sa sortie dans une chaîne de caractères.
    • Extrait les `$data` en variables locales accessibles dans la vue.
    • Utilisée par `view()` pour le contenu et le layout.
  • Méthodes `json(...)` et `redirect(...)` : Raccourcis pour créer des objets `Response` de type JSON ou redirection.
  • Méthode `flash(string $type, string $message)` : Pour enregistrer des messages flash en session.

5.5 Authentification (src/Lib/Auth.php)

Classe statique gérant l'authentification, la session utilisateur et les vérifications de permissions.

  • `Auth::login(string $username, string $password)` :
    • Vérifie les identifiants contre la base de données (via `User::findByUsername()`).
    • Utilise `password_verify()` pour le mot de passe.
    • Si succès, enregistre `user_id` en session et régénère l'ID de session.
  • `Auth::logout()` : Détruit la session utilisateur.
  • `Auth::isLoggedIn()` : Vérifie si un utilisateur est connecté.
  • `Auth::user()` : Retourne l'objet `User` de l'utilisateur connecté (avec une mise en cache statique simple pour la requête actuelle).
  • `Auth::id()` : Retourne l'ID de l'utilisateur connecté.
  • `Auth::protect(...)` : Redirige vers la page de connexion si l'utilisateur n'est pas connecté.
  • `Auth::can(string $permissionName)` :
    • Récupère l'utilisateur connecté.
    • Appelle la méthode `$user->hasPermission($permissionName)` de l'objet `User`.
  • `Auth::hasRole(string $roleName)` : (Méthode de convenance) Vérifie si l'utilisateur connecté a un rôle spécifique.

5.6 Modèles Principaux (src/Models/)

Les modèles sont responsables de l'interaction avec la base de données et de l'encapsulation de la logique métier liée aux données. Ils utilisent PDO pour les requêtes SQL, avec des requêtes préparées pour la sécurité. La plupart des modèles ont une méthode `hydrate()` privée statique pour convertir un tableau de données de la BDD en une instance de l'objet modèle.

Modèle `User.php`

Gère les données des utilisateurs, leurs rôles et leurs permissions.

  • Propriétés clés : `id`, `username`, `password_hash`, `email`, `first_name`, `last_name`, `is_active`, `site_id` (FK vers `sites`), `roles` (tableau d'objets `Role`), `site` (objet `Site` chargé).
  • Méthodes CRUD :
    • `findById(int $id)`: Récupère un utilisateur par ID.
    • `findByUsername(string $username)`: Récupère un utilisateur par nom d'utilisateur.
    • `findByEmail(string $email)`: Récupère un utilisateur par email.
    • `getAll(array $filters = [], ...)`: Récupère tous les utilisateurs, avec filtres (notamment par `site_id`) et jointure optionnelle sur les sites pour afficher le nom/code du site.
    • `create(array $data)`: Crée un nouvel utilisateur, incluant le hashage du mot de passe et l'assignation optionnelle de `site_id`.
    • `update(int $id, array $data)`: Met à jour un utilisateur, gère la mise à jour du mot de passe (si fourni) et du `site_id`.
    • `delete(int $id)`: Suppression physique d'un utilisateur (à utiliser avec précaution).
  • Gestion des Rôles :
    • `loadRoles()`: Charge les objets `Role` associés à l'utilisateur depuis la table `user_roles` et les stocke dans `$this->roles`.
    • `assignRole(int $roleId)`, `revokeRole(int $roleId)`: Gèrent les entrées dans `user_roles`.
    • `syncRoles(array $roleIds)`: Synchronise les rôles de l'utilisateur avec la liste d'IDs fournie (ajoute les nouveaux, supprime les anciens).
    • `hasRole(string $roleName)`: Vérifie si l'utilisateur possède un rôle spécifique par son nom.
  • Gestion des Permissions (via les rôles) :
    • `hasPermission(string $permissionName)`: Vérifie si l'utilisateur a une permission donnée en parcourant les permissions de tous ses rôles. Appelle `Role::hasPermission()` pour chaque rôle.
  • Gestion du Site :
    • `loadSite()`: Charge l'objet `Site` associé (si `site_id` est défini) et le stocke dans `$this->site`.

Modèle `Site.php`

Gère les informations des sites opérationnels.

  • Propriétés clés : `id`, `code` (unique), `name`, `address`, `is_active`.
  • Méthodes CRUD :
    • `findById(int $id)`, `findByCode(string $code)`: Récupération par ID ou code.
    • `getAllActive()`: Récupère uniquement les sites actifs (pour les dropdowns de sélection).
    • `getAll()`: Récupère tous les sites (pour la gestion).
    • `create(array $data)`: Crée un nouveau site.
    • `update(int $id, array $data)`: Met à jour un site.
    • `setActiveStatus(int $id, bool $isActive)`: Active ou désactive un site (soft delete).
    • `forceDelete(int $id)`: Suppression physique (utilisation exceptionnelle).

Modèle `Role.php`

Gère les rôles et leur association avec les permissions.

  • Propriétés clés : `id`, `name` (unique), `description`, `permissions` (tableau d'objets `Permission`).
  • Méthodes CRUD : `findById(int $id)`, `findByName(string $name)`, `getAll()`, `create(...)`, `update(...)`, `delete(...)`.
  • Gestion des Permissions :
    • `loadPermissions()`: Charge les objets `Permission` associés au rôle depuis `role_permissions` et les stocke dans `$this->permissions`.
    • `assignPermission(int $permissionId)`, `revokePermission(int $permissionId)`: Gèrent les entrées dans `role_permissions`.
    • `syncPermissions(array $permissionIds)`: Synchronise les permissions du rôle.
    • `hasPermission(string $permissionName)`: Vérifie si le rôle possède une permission spécifique.

Modèle `Permission.php`

Gère les permissions de l'application.

  • Propriétés clés : `id`, `name` (code unique de la permission), `description`.
  • Méthodes CRUD : `findById(int $id)`, `getAll()`, `create(...)`, `update(...)`, `delete(...)`.
  • *(Actuellement, pas de méthode `findByName()` implémentée, mais serait utile pour des vérifications d'unicité plus robustes avant insertion.)*

Modèle `PackingList.php`

Gère les listes de colisage.

  • Propriétés clés : `id`, `site_id` (FK), `reference` (unique), `ship_date`, `status` ('open', 'closed'), `created_by_user_id`, `closed_by_user_id`, `site` (objet `Site`), `paletteCount` (optionnel, pour affichage).
  • Méthodes principales :
    • `create(string $shipDateString, ?int $siteId, ?int $userId)`: Crée une PL. Appelle `ReferenceGenerator::generate()` pour la référence, en tenant compte du `$siteId` pour les patrons et compteurs par site.
    • `findById(int $id)`, `getAll(array $filters, ...)` (filtre par site, jointure sur site).
    • `updateShipDate(int $id, string $newShipDate)`: Modifie la date d'expédition si PL ouverte.
    • `close(int $id, ?int $userId)`: Ferme la PL. Gère le statut des palettes associées (ferme celles ouvertes et non vides, supprime celles générées et vides).
    • `reopen(int $id)`: Réouvre une PL fermée.
    • `delete(int $id)`: Supprime une PL (si conditions remplies : ouverte, pas de palettes actives/fermées).
    • `getPaletteCount()`: Compte les palettes associées.
    • `loadSite()`: Charge l'objet `Site` associé.
    • *(Anciennement `getAllColis()`, maintenant remplacé par `Colis::findAllByPackingListId()` pour une meilleure séparation des responsabilités).*

Modèle `Palette.php`

Gère les palettes.

  • Propriétés clés : `id`, `packing_list_id` (FK), `code` (unique), `qr_code_path`, `status` ('generated', 'open', 'closed'), `max_colis`, `open_date_time`, `close_date_time`, `colisCount` (optionnel), `packingListReference` (optionnel), `siteName` (optionnel).
  • Méthodes principales :
    • `create(int $packingListId, ?int $userId)`: Crée une palette. Appelle `ReferenceGenerator::generate()` pour le code et `QrCodeService::generateAndSavePaletteQrCode()` pour le QR code. Récupère le `site_id` de la PL parente pour le passer au `ReferenceGenerator`.
    • `findById(int $id)`, `findByCode(string $code)`, `findByPackingListId(int $packingListId)`, `getAllFiltered(array $filters)`.
    • `open(int $id, int $maxColis, ?int $userId)`: Ouvre une palette `generated`, enregistre `max_colis`.
    • `updateMaxColis(int $id, int $newMaxColis)`: Modifie `max_colis` d'une palette ouverte.
    • `updateFields(int $id, array $dataToUpdate)`: Méthode générique pour mettre à jour des champs (utilisée par `closePalette`).
    • `reopen(int $id)`: Réouvre une palette fermée (si sa PL parente est ouverte).
    • `deleteById(int $id)`: Suppression physique (conditions vérifiées dans le contrôleur).
    • `getColisCount()`: Compte les colis sur la palette.

Modèle `Colis.php`

Gère les colis scannés.

  • Propriétés clés : `id`, `palette_id`, `package_number`, `payload_json`, `scan_date_time`, `type` (`parent` ou `product`), `parent_colis_id`, `comment`, et tous les champs parsés du payload (`client_name`, `of_number`, ..., `line_number`). Propriétés optionnelles pour jointures : `palette_code`, `packing_list_reference`, `site_name`, `site_code`. Chaque colis possède également un tableau children pour ses éventuels enfants.
  • Méthodes principales :
    • `create(array $data)`: Enregistre un nouveau colis avec toutes ses informations (parsées et le JSON brut).
    • `findById(int $id)`, `findByPaletteId(int $paletteId, ...)` (liste les colis d'une palette).
    • `findAllByPackingListId(int $packingListId, ...)`: Récupère tous les colis d'une PL (via jointure sur palettes).
    • `packageNumberExists(string $packageNumber)`: Vérifie l'unicité d'un `package_number`.
    • `deleteById(int $id)`: "Dé-scanner" un colis.
    • `moveToPalette(int $colisId, int $newPaletteId)`: Change le `palette_id` d'un colis.
    • `findChildren(int $parentId)`: Retourne la liste des colis enfants d'un colis parent.
    • `updateComment(int $colisId, ?string $comment)`: Met à jour le commentaire d'un colis.
    • `getScannedQuantitiesBySite(...)`, `getScannedQuantitiesByPackingList(...)`, `countScannedTodayBySite(...)`: Méthodes d'agrégation pour les statistiques et le suivi des écarts.

Modèle `Setting.php`

Gère les paramètres de l'application stockés en base de données.

  • Méthodes clés :
    • `get(string $key, mixed $default = null)`: Récupère la valeur d'un paramètre.
    • `set(string $key, mixed $value, ?string $description = null)`: Définit/Met à jour un paramètre.
    • `getAllAsKeyValue()`, `getAllDetails()`: Pour récupérer tous les paramètres.

Modèle `DynamicCounter.php`

Gère les compteurs séquentiels utilisés par `ReferenceGenerator`.

  • Méthodes clés :
    • `getNextValue(string $counterKey)`: Récupère la valeur actuelle d'un compteur, l'incrémente, et retourne la nouvelle valeur. Gère la création du compteur avec `INSERT ... ON DUPLICATE KEY UPDATE`. La `counterKey` inclut des informations de portée (type d'entité, site, année, mois) pour assurer l'unicité et la réinitialisation des séquences.
    • `resetCounter(string $counterKey, int $value = 0)`: Réinitialise un compteur.

Modèle `TheoreticalExport.php`

Gère les données théoriques d'expédition importées.

  • Propriétés clés : `site_id`, `import_year`, `import_week`, `of_number`, `order_number`, `sku`, `expected_quantity`.
  • Méthodes clés :
    • `deleteBySiteWeek(int $siteId, int $year, int $week)`: Supprime les entrées d'un site/semaine avant un nouvel import.
    • `insertBatch(array $rowsData)`: Insère un lot de données théoriques.
    • `getBySiteWeek(int $siteId, int $year, int $week, array $filters = [])`: Récupère le théorique pour comparaison.

5.7 Services Utilitaires (src/Services/)

Service `ReferenceGenerator.php`

Responsable de la génération des chaînes de caractères uniques (références, codes) basées sur des patrons configurables.

  • Méthode `generate(string $patternKey, int $entityId, ?int $siteId, array $additionalPlaceholders, ?DateTimeInterface $dateContext)` :
    • Récupère le patron depuis `Setting::get($patternKey)`.
    • Remplace les placeholders comme `{YYYY}`, `{MM}`, `{DD}`, `{WW}` (semaine), `{ID_PL}`, `{ID_PALETTE}`, `{SITE_CODE}`.
    • Gère les compteurs dynamiques (ex: `{COUNTER_YEARLY_SITE_4DIGITS}`) :
      • Construit une `counter_key` unique pour `DynamicCounter` en fonction de la portée du compteur (global, annuel, mensuel, quotidien, hebdomadaire), du type d'entité, et optionnellement du `siteId` (si `_SITE` est dans le placeholder du compteur).
      • Appelle `DynamicCounter::getNextValue()` pour obtenir la prochaine valeur.
      • Formate le compteur avec des zéros non significatifs (`str_pad`).

Service `QrCodeService.php`

Gère la génération et la sauvegarde des images QR code en utilisant la librairie `endroid/qr-code`.

  • Constructeur : Initialise les chemins de stockage et publics pour les QR codes, vérifie/crée le dossier de stockage et vérifie l'extension GD.
  • Méthode `generateAndSavePaletteQrCode(string $dataToEncode, string $filename, ?string $labelText)` :
    • Prend les données à encoder (le code de la palette), un nom de fichier, et un label optionnel.
    • Utilise la librairie `endroid/qr-code` (en instanciant directement `QrCode` et `Label`, puis en utilisant `PngWriter`) pour créer une image PNG.
    • Sauvegarde l'image dans public/qrcodes/palettes/.
    • Retourne le chemin public URL vers l'image générée (ou `false` en cas d'échec).
  • `getPaletteQrCodePublicPath(string $filename)` : Retourne le chemin public d'un QR code existant.

7. Flux de Données et Logiques Métier Clés

Cette section décrit les principaux processus métier et comment ils sont implémentés.

7.1 Création d'une Packing List (Multi-Sites)

  1. L'utilisateur (Superviseur/Admin) accède à la page de création de PL (action `PackingListController::create`).
  2. La vue packing_lists/create.php s'affiche.
    • Le contrôleur détermine les sites pour lesquels l'utilisateur peut créer une PL (via `getAvailableSitesForCurrentUser()`).
    • Un dropdown permet de sélectionner le `site_id`.
    • L'utilisateur saisit la `ship_date`.
  3. L'utilisateur soumet le formulaire (action `PackingListController::store`).
  4. Le contrôleur valide les données (date, `site_id` valide et autorisé pour l'utilisateur).
  5. Si valide, `PackingList::create(shipDate, siteId, userId)` est appelée.
  6. Dans `PackingList::create()`:
    1. Début de transaction.
    2. Insertion d'une ligne dans `packing_lists` avec une référence temporaire, le `site_id`, `ship_date`, statut 'open', et `created_by_user_id`.
    3. Récupération du `lastInsertId()` (ID de la nouvelle PL).
    4. Appel à `ReferenceGenerator::generate('packing_list_reference_pattern', lastId, siteId, siteCodePlaceholder, shipDateTime)` pour obtenir la référence finale.
      • `ReferenceGenerator` récupère le patron depuis `settings`.
      • Il remplace les placeholders de date, l'ID (`{ID_PL}`), et le code du site (`{SITE_CODE}`).
      • Pour les compteurs (ex: `{COUNTER_YEARLY_SITE_4DIGITS}`), il construit une `counter_key` (incluant `siteId` si `_SITE` est dans le placeholder) et appelle `DynamicCounter::getNextValue()`.
    5. Mise à jour de la ligne `packing_lists` avec la `reference` finale.
    6. Commit de la transaction.
    7. Retourne l'objet `PackingList` créé.
  7. Si la création réussit, le contrôleur redirige vers la page de détail de la nouvelle PL (`packing_lists/show/{id}`).

7.2 Génération de Code Palette (Multi-Sites, QR Code)

  1. Depuis la page de détail d'une PL ouverte (`packing_lists/show/{id}`), l'utilisateur clique sur "Générer Palette Unique" ou soumet le formulaire "Multi-Palettes" (action `PaletteController::storeForPackingList` ou `PackingListController::generateMultiplePalettes` qui appelle `Palette::create` en boucle).
  2. L'action du contrôleur vérifie que la PL est ouverte et que l'utilisateur a la permission `palette_create`.
  3. Elle appelle `Palette::create(packingListId, userId)`.
  4. Dans `Palette::create()`:
    1. Début de transaction.
    2. Récupère la PL parente pour obtenir son `site_id` et `site_code` (si le patron palette les utilise).
    3. Insertion d'une ligne dans `palettes` avec `packing_list_id`, statut 'generated', `created_by_user_id`, et un `code` temporaire.
    4. Récupération du `lastInsertId()` (ID de la nouvelle palette).
    5. Appel à `ReferenceGenerator::generate('palette_code_pattern', lastId, siteIdDeLaPL, siteCodeDeLaPLPlaceholder, now)` pour le code final.
    6. Instanciation de `QrCodeService`.
    7. Appel à `qrCodeService->generateAndSavePaletteQrCode(finalCode, nomFichierUnique, finalCode)` pour créer l'image PNG du QR code dans public/qrcodes/palettes/. Cette méthode retourne le chemin public relatif de l'image.
    8. Mise à jour de la ligne `palettes` avec le `code` final et le `qr_code_path`.
    9. Commit de la transaction.
    10. Retourne l'objet `Palette` créé.
  5. Le contrôleur redirige vers la page de détail de la PL, qui affiche maintenant la nouvelle palette.

7.3 Processus de Scan de Colis

Ce processus se déroule principalement sur la page colis/scan.php.

  1. Activation de la Palette :
    • L'opérateur accède à `/colis/scan`.
    • Il scanne/saisit le code d'une palette dans le champ dédié.
    • Le formulaire est soumis à `ColisController::processPaletteForScan`.
    • Le contrôleur vérifie la palette :
      • Si inexistante ou PL parente fermée : erreur.
      • Si statut `closed` : erreur.
      • Si statut `generated` : redirection vers `palettes/show/{id}` pour que l'opérateur l'ouvre (saisie de `max_colis` via `PaletteController::processOpening` qui appelle `Palette::open()`). L'opérateur doit ensuite revenir à l'interface de scan.
      • Si statut `open` : l'ID de la palette est stocké dans `$_SESSION['active_scan_palette_id']`. Redirection vers `/colis/scan`.
    • La page `/colis/scan` (via `ColisController::scanInterface`) affiche les détails de la palette active (s'il y en a une) et met le focus sur le champ de scan colis.
  2. Scan d'un Colis :
    • L'opérateur scanne le QR code d'un colis dans le champ dédié. Le scanner simule une saisie clavier + "Entrée".
    • Le JavaScript de la page intercepte "Entrée" et soumet le formulaire contenant le payload brut du QR code à `ColisController::processColisScan`.
    • Dans `ColisController::processColisScan` :
      1. Vérifie qu'une palette est active en session et qu'elle est toujours `open`.
      2. Parse le payload brut (valeurs séparées par `;` dans un ordre fixe ou ancien format `cle|valeur;...`) en un tableau associatif.
      3. Reconstruit une chaîne JSON valide à partir de ce tableau pour stockage dans `payload_json`.
      4. Si le tableau parsé ne contient que `package_number`, un colis de type parent est créé et son identifiant est stocké en session.
      5. Les scans suivants deviennent des colis product avec parent_colis_id renseigné.
      6. Scanner à nouveau le même numéro met fin au groupage (le parent est "fermé").
      7. Dans les autres cas, le payload complet est utilisé : extraction de `package_number`, `of_number`, `sku`, `quantity`, etc., y compris les nouveaux champs comme `ref_interne`.
      8. Effectue les validations :
        • `package_number` présent.
        • Capacité de la palette non dépassée (`Palette::getColisCount() < $activePalette->max_colis`).
        • `package_number` non déjà existant en base (`Colis::packageNumberExists()`).
      9. Si erreurs : message flash d'erreur (potentiellement avec écran rouge via session), redirection vers `/colis/scan`.
      10. Si valide : prépare un tableau `$colisData` avec tous les champs (y compris `palette_id`, `scanned_by_user_id`, `scan_date_time`, `payload_json` et les champs parsés).
      11. Appelle `Colis::create($colisData)`.
      12. Message flash de succès, redirection vers `/colis/scan` pour le prochain scan.

7.4 Gestion des Permissions

L'accès aux fonctionnalités est contrôlé par un système de rôles et permissions.

  • Chaque utilisateur a un ou plusieurs rôles (`user_roles`).
  • Chaque rôle a une ou plusieurs permissions (`role_permissions`).
  • La classe `App\Lib\Auth` fournit des méthodes statiques :
    • `Auth::can(string $permissionName)` : Vérifie si l'utilisateur connecté possède la permission spécifiée. Elle récupère l'objet `User` et appelle `$user->hasPermission()`.
    • `User::hasPermission(string $permissionName)` : Itère sur les rôles de l'utilisateur et appelle `$role->hasPermission()` pour chaque.
    • `Role::hasPermission(string $permissionName)` : Itère sur les permissions directes du rôle (après les avoir chargées via `$role->loadPermissions()`) et vérifie si le nom de la permission correspond.
  • La méthode `BaseController::authorize(string $permissionName, ...)` est utilisée au début des méthodes d'action des contrôleurs pour protéger l'accès. Elle appelle `Auth::can()` et redirige si la permission est manquante.
  • Les vues utilisent également `Auth::can()` pour afficher ou masquer conditionnellement des liens et des boutons d'action.

Les permissions "méta" (ex: `user_manage`, `role_manage`) sont utilisées dans les constructeurs des contrôleurs d'administration pour un contrôle global, tandis que des permissions plus granulaires (ex: `packinglist_create`, `palette_open`) sont utilisées pour des actions spécifiques.

8. Déploiement et Configuration Serveur (Bases)

Pour déployer l'application sur un serveur de production :

  1. Prérequis Serveur :
    • Serveur web (Apache ou Nginx).
    • PHP (version 8.2+ recommandée, compte tenu des dépendances).
    • Base de données MySQL ou MariaDB.
    • Extension PHP : `pdo_mysql`, `gd` (pour les QR codes), `mbstring`, `json`, `intl` (pour `NotoSans` et internationalisation si besoin).
    • Composer installé sur le serveur (pour `composer install --no-dev --optimize-autoloader`) ou uploader le dossier `vendor`.
  2. Configuration Apache :
    • Le `DocumentRoot` doit pointer vers le dossier public/ de l'application.
    • `AllowOverride All` doit être activé pour le dossier `public/` afin que le fichier .htaccess soit pris en compte pour la réécriture d'URL.
    • `mod_rewrite` doit être activé.
  3. Fichier de Configuration (config/config.php) :
    • Les constantes `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` doivent être ajustées pour l'environnement de production.
    • La détection dynamique de `APP_URL` et `BASE_URL` devrait fonctionner, mais vérifiez qu'elle produit les bonnes URL pour votre domaine de production.
    • **IMPORTANT :** Mettre `ini_set('display_errors', 0);` et `error_reporting(0);` (ou un niveau plus restrictif comme `E_ALL & ~E_DEPRECATED & ~E_STRICT`) pour ne pas afficher les erreurs PHP aux utilisateurs finaux. Les erreurs doivent être logguées (voir ci-dessous).
  4. Logs en Production :
    • Configurez `php.ini` pour que `log_errors = On` et que `error_log` pointe vers un fichier de log accessible mais non public.
    • Vérifiez la configuration `ErrorLog` d'Apache.
  5. Permissions des Dossiers :
    • Le serveur web doit avoir les droits d'écriture sur les dossiers utilisés pour le stockage (ex: public/qrcodes/palettes/) et les logs (ex: logs/ si vous l'utilisez).
    • Les autres fichiers de l'application doivent être lisibles par le serveur web.
  6. Composer :
    • Sur le serveur, après avoir cloné/uploadé le code, exécutez `composer install --no-dev --optimize-autoloader`. L'option `--no-dev` exclut les dépendances de développement, et `--optimize-autoloader` crée un autoloader plus performant.
  7. Sécurité :
    • Assurez-vous que seul le dossier `public/` est accessible via le web.
    • Utilisez HTTPS.
    • Revoyez toutes les configurations de sécurité PHP et serveur.
